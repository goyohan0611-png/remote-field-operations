# 문제 해결 사례

## 현장 네트워크 변화에 대한 의존 줄이기

**문제:** 공인 IP·공유기·포트포워딩 설정이 바뀌면 기존 접속 경로를 다시 점검해야 했습니다.

**접근:** 현장 PC와 관리 PC 사이에 Tailscale 연결을 구성하고, 현장 PC를 통해 내부 장비에 접근하는 구조를 사용했습니다. 상태 수집은 현장 에이전트가 중앙 서버로 먼저 보고하도록 분리했습니다.

**판단:** 연결 문제와 장비 문제를 구분할 수 있는 관측 항목이 필요합니다. 터널이 있더라도 현장 PC가 꺼지거나 내부 장비가 응답하지 않으면 관리할 수 없습니다.

## 여러 현장의 동일한 내부 IP

**문제:** 서로 다른 현장이 같은 내부 IP 대역을 사용하는 상황에서 단순 IPv4 경로만으로는 대상 현장을 구분하기 어려웠습니다.

**접근:** 현장 식별값을 포함하는 4via6 주소와 서브넷 경로를 사용했습니다.

**판단:** 현장 식별값은 중복되지 않게 관리해야 합니다. 장비의 Tailscale IP, 서브넷 경로, 개별 장비의 4via6 주소를 구분해 표시·문서화해야 합니다. 인증된 노드라고 모든 경로가 자동으로 승인되는 것은 아닙니다.

## IPv4 전용 카메라 앱

**문제:** 기존 카메라 제어 프로그램이 IPv6 목적지를 입력받지 못했습니다.

**접근:** 관리자 PC의 루프백 IPv4 주소와 임시 포트를 열고, 카메라 앱의 TCP 연결을 터널 목적지로 중계했습니다.

**판단:** 주소 입력창의 길이만 늘리는 것으로는 소켓 계층의 IPv6 제약이 해결되지 않습니다. 기존 앱과 장비를 바꾸지 않고 연결 계층을 보완하는 방법을 선택했습니다. 프록시의 수명·오류·연결 정리도 함께 다뤄야 합니다.

## 무인 등록과 비밀값 보관

**문제:** 모든 현장에서 관리 계정으로 로그인하는 절차는 번거롭고, 장기 비밀값을 배포하면 회수와 관리가 어려워집니다.

**접근:** 중앙 서버가 등록 요청을 확인한 후 단기 일회용 인증키를 발급하도록 구성했습니다. 장기 OAuth 자격증명은 서버에만 둡니다.

**판단:** 등록키가 있다는 것과 현장 접근 권한이 있다는 것은 다릅니다. 태그, 접근 정책, 경로 승인, 대상 장비 계정을 구분해야 합니다.

## 파일 작업과 업데이트의 실패 가능성

**문제:** 원격 파일 삭제와 업데이트는 상태 표시와 달리 실제 데이터를 바꾸며, 중간 실패의 영향도 큽니다.

**접근:** 파일 작업에서 대상·경로·파일 종류 검증을 다루고, 업데이트에서는 배포 파일 검증·기존 버전 보관·성공 확인·실패 시 복구 흐름을 다뤘습니다.

**판단:** ‘실행 요청 성공’과 ‘장비 작업 완료’를 혼동하지 않아야 합니다. 실제 환경 검증 없이 무중단·자동 복구 성공률을 보장하지 않습니다. 이 공개 데모에는 삭제·업데이트 실행 기능 자체를 넣지 않았습니다.

## 검증의 범위

개발 과정에서 정적 검사·자동 테스트와 현장 PC·녹화기·카메라 연결 시험을 활용했습니다. 이 저장소의 테스트는 **공개용 가상 데이터 데모**만 검사합니다. 원본 운영 제품 전체의 현재 품질이나 실제 고객 환경에서의 가동률을 인증하는 테스트가 아닙니다.

## 향후 아이디어와 완료 기능 구분

정해진 접근 통로와 장비 API를 결합하면 이상 상태 진단, 업로드 재시도, 설정 변경 지원 등으로 확장할 수 있습니다. 다만 AI가 실제 장비를 조작하려면 대상·작업 허용목록, 사용자 승인, 감사 기록, 실패 시 중단·복구 같은 별도 설계가 필요합니다. 이 내용은 **확장 가능성**이며, 무인 자동 CS를 구현·운영했다는 주장이 아닙니다.
