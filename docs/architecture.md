# 시스템 구조

## 두 경로를 구분하기

원격 관리 시스템에서는 **상태를 보고하는 경로**와 **장비에 접근하는 경로**를 구분해야 합니다.

### 상태 수집

현장 에이전트가 로컬 상태를 읽고 HTTPS로 중앙 서버에 보고합니다. 중앙 서버가 현장별 상태를 관리하고, 관리 앱이 이를 조회·갱신합니다. 에이전트의 최신 보고 시각과 장비 서비스 상태는 다른 정보이므로 각각 표시합니다.

### 장비 접근

관리자 PC가 Tailscale 통로를 통해 현장 PC의 서브넷 라우터에 도달합니다. 현장 PC는 패킷을 내부 장비에 전달하고 응답도 돌려보냅니다. 원격 장비의 SSH·웹 서비스 등을 그대로 이용하는 것이며, 관리자 명령을 현장 PC에서 대신 실행하는 방식과는 구분합니다.

연결 경로는 네트워크 조건에 따라 직접 연결 또는 중계 경로가 될 수 있습니다. 특정 경로를 항상 보장하지 않습니다.

## 구성요소의 책임

| 구성요소 | 책임 | 다른 구성요소와 구분되는 점 |
| --- | --- | --- |
| 관리 데스크톱 | 현장 조회, 상태 표시, 관리 도구 실행 연계 | 장비 프로토콜을 Tailscale API로 대체하지 않음 |
| 중앙 서버 | 등록·인증, 상태 관리, 등록키 발급 연계 | 모든 장비 트래픽의 필수 중계 서버가 아님 |
| 현장 에이전트 | 로컬 상태 수집, 상태 보고, 허용된 관리 기능 | Tailscale 자체와 별도 프로그램 |
| 현장 Tailscale 노드 | 장비 간 연결과 승인된 서브넷 전달 | 내부 장비의 계정·서비스를 대신 제공하지 않음 |
| 내부 장비 | SSH·FTP·웹·카메라 제어 등 실제 서비스 | 설치되지 않은 기능은 터널로 생기지 않음 |

## 중복 IP와 4via6

서로 다른 현장이 같은 IPv4 대역을 사용하면 목적지 IPv4만으로는 경로가 모호해집니다. 4via6는 현장 식별값과 IPv4 정보를 IPv6 주소에 함께 표현하는 Tailscale 기능입니다.

예를 들어 ‘현장 A의 장비 주소’와 ‘현장 B의 동일한 장비 주소’를 서로 다른 목적지로 표현할 수 있습니다. 현장 PC의 라우터가 해당 경로를 광고하고, 승인된 경로와 접근 정책이 맞아야 합니다.

이 저장소는 실제 현장 배정과 접속 주소를 제공하지 않습니다. 데모의 PC 주소는 설명용 문서 대역이고, 내부 IP와 4via6는 합성 현장 ID·일반적인 예시 대역으로 계산합니다. 화면에 표시되어도 실제 접속 대상으로 사용하지 않습니다.

## 카메라 앱의 IPv4 제약 보완

```text
기존 IPv4 전용 카메라 앱
  → 관리자 PC의 127.0.0.1:임시 포트
  → 관리자 PC에서 실행되는 로컬 TCP 프록시
  → Tailscale의 4via6 목적지
  → 현장 서브넷 라우터
  → 내부 IPv4 카메라
```

프록시는 관리자 PC에 있습니다. 카메라 펌웨어나 제어 앱 자체를 수정한 것이 아닙니다. 관리 앱을 종료하면 프록시 연결도 정리해야 합니다. 단순 TCP 제어 연결을 다룬 접근이며, UDP·멀티캐스트·추가 미디어 채널까지 자동 지원한다고 일반화하지 않습니다.

## 자동 등록 흐름

1. 관리 측에서 현장 등록 코드를 발급합니다.
2. 현장 설치 프로그램이 유효한 등록 코드로 중앙 서버에 등록합니다.
3. 서버가 서버 측 OAuth 자격증명으로 단기 일회용 Tailscale 인증키를 발급합니다.
4. 현장 PC에서 Tailscale 등록과 태그·현장 경로 설정을 진행합니다.
5. 필요한 경로 승인과 접근 정책을 확인합니다.

장기 비밀값을 설치 파일에 넣지 않는 것이 핵심입니다. 자동 등록키 발급과 무인 설치가 있더라도 경로·정책 검증을 생략하지 않습니다.

## 실패를 구분하기

- 에이전트 미응답: PC 전원, 인터넷, 서비스, 서버 연결 등 확인.
- Tailscale 미연결: 인증·클라이언트 상태 등 확인.
- 경로 없음: 광고 경로·경로 승인·접근 정책 확인.
- 연결되지만 장비 서비스 실패: 실제 내부 장비·포트·계정·프로토콜 확인.

상태 하나만으로 원인을 확정하지 않도록, 관측 결과와 진단 판단을 분리합니다.
